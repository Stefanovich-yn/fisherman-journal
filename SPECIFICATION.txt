Layered ArchitectureEquipment Rental Service — самостоятельная реализация многослойного приложенияФОРМАТ	ТЕХНОЛОГИИ	ХРАНЕНИЕ	РЕЗУЛЬТАТИндивидуально	Java 25 · Console	Текстовый файл	Работающий Eclipse-проектЦель задания. Самостоятельно спроектировать и реализовать небольшое приложение с многослойной архитектурой, повторив полный путь обработки запроса: Controller → Logic → DAO → File и обратное формирование ответа.Важно. Это контрольное задание. Готовый каркас классов не предоставляется: структуру проекта, интерфейсы, реализации и связывание компонентов необходимо определить самостоятельно, соблюдая требования ниже.1. Предметная областьFisherman's Journal предназначено для регистрации уловов рыболовов-любителей или членов рыболовного клуба. Пользователь может зафиксировать запись об улове (указав рыбака, рыбу, вес, количество и место поимки), изменить статус записи, найти уловы по различным критериям, а также получить агрегированную статистику.Сущность CatchRecord (Запись об улове)1. id — уникальный положительный идентификатор;2. fishermanName — имя рыбака;3. fishType — вид рыбы (например, Щука, Судак, Окунь);4. quantity — количество пойманных единиц рыбы данного вида;5. weight — общий вес улова в граммах;6. waterBody — наименование водоёма (места поимки);7. status — текущий статус записи;8. createdAt — дата и время создания записи.Допустимые статусы (RecordStatus): NEW, VERIFIED, REGISTERED, ARCHIVED, CANCELLEDСоздание записи. Новая запись всегда получает статус NEW. Идентификатор и createdAt назначаются приложением, а не передаются пользователем.2. Функциональные требованияКоманда	Назначение	ПараметрыCREATE_RECORD	Создать новую запись об улове	fisherman, fish, quantity, weight, waterBodyCHANGE_STATUS	Изменить статус существующей записи	id, statusFIND_BY_FISHERMAN	Найти записи конкретного рыбака	fishermanFIND_BY_FISH	Найти записи по виду рыбы	fishFIND_BY_WATERBODY	Найти записи по названию водоёма	waterBodyGET_STATS	Получить сводную статистику по рыбаку	fishermanSHOW_ACTIVE	Показать активные (незавершённые) записи	параметры не нужныSHOW_ALL	Показать все записи в журнале	параметры не нужныФормат входного запросаПервая строка содержит имя команды. Каждая следующая строка содержит один параметр в формате name=value. Порядок параметров может быть фиксированным или определяться по имени — выбранный подход необходимо применять последовательно.Примеры запросов:```textCREATE\_RECORDfisherman=Ivan Petrovfish=Pikequantity=3weight=4500waterBody=Volga RivercodeTextCHANGE\_STATUSid=1status=VERIFIEDcodeTextFIND\_BY\_FISHERMANfisherman=IvancodeTextFIND\_BY\_FISHfish=pikecodeTextFIND\_BY\_WATERBODYwaterBody=volgacodeTextGET\_STATSfisherman=Ivan Petrov```Ответ контроллера: Строка с понятным результатом операции. Точный текст не фиксируется, но по ответу должно быть ясно, выполнена операция или отклонена и почему.Для команды GET_STATS ответ должен содержать агрегированные данные.Пример формата ответа:«Рыбак Ivan Petrov: всего уловов — 5, поймано рыбы — 14 шт., общий вес — 12500г, самый крупный улов — Щука (4500г)».3. Бизнес-правила1. fishermanName и fishType не должны быть пустыми или состоять только из пробелов.2. waterBody не должен быть пустым, а его длина должна находиться в диапазоне от 3 до 50 символов включительно.3. quantity (количество рыбы) должно находиться в диапазоне от 1 до 100 штук включительно.4. weight (общий вес улова в граммах) должен находиться в диапазоне от 100 до 30 000 грамм включительно.5. Поиск по полям fishermanName, fishType и waterBody выполняется без учёта регистра и не требует полного совпадения строки (достаточно частичного вхождения).6. SHOW_ACTIVE возвращает все записи, статус которых не ARCHIVED и не CANCELLED.7. Изменение статуса разрешено только для существующей записи.Разрешённые переходы статусов1. NEW → VERIFIED или CANCELLED;2. VERIFIED → REGISTERED или CANCELLED;3. REGISTERED → ARCHIVED;4. ARCHIVED и CANCELLED — финальные статусы: дальнейшее изменение запрещено.Расположение правил. Проверка диапазонов, валидация полей улова, поиск, расчёт статистики (GET_STATS через Stream API) и проверка допустимости переходов статусов относятся к logic-слою. Controller проверяет структуру запроса, а DAO отвечает только за чтение и запись данных.4. Архитектурные требования`Main → Controller / Commands → Logic → DAO → catch\_records.txt`Создайте как минимум следующие пакеты:1. entity — CatchRecord и RecordStatus (enum);2. controller — Controller, Command, CommandName (enum), CommandProvider;3. controller.impl — отдельная реализация Command для каждой поддерживаемой команды и команда для неизвестного запроса;4. logic — интерфейс RecordService (или Logic), LogicException и точка получения реализации;5. logic.impl — реализация бизнес-логики;6. dao — DAO-интерфейс, DaoException и точка получения реализации;7. dao.impl — файловая реализация DAO;8. main — демонстрационный запуск приложения.Обязанности слоёвController. извлекает имя команды, получает Command, передаёт запрос на выполнение и возвращает строковый ответ; не содержит бизнес-правил и не работает с файлом.Command. разбирает параметры конкретной команды, проверяет формат запроса, вызывает logic-слой и преобразует результат или LogicException в пользовательский ответ.Logic. проверяет бизнес-правила, управляет переходами статусов, выполняет поиск и вызывает DAO; не знает формат строкового запроса.DAO. сохраняет, читает и обновляет RentalOrder в текстовом файле; преобразует IOException и ошибки чтения данных в DaoException.Entity. хранит состояние предметной области и не зависит от controller, logic или dao.Main. создаёт или получает Controller, отправляет несколько запросов и выводит ответы; не выполняет работу других слоёв.Интерфейсы и реализации1. Logic и DAO должны быть представлены интерфейсами и отдельными классамиреализациями. LAYERED ARCHITECTURE Страница 42. Controller и команды должны зависеть от контракта logic-слоя, а logic — от контракта DAO, а не от конкретных реализаций.3. Для предоставления реализаций можно использовать Provider, Singleton-provider или явную передачу зависимостей через конструктор. Выбранный способ должен быть единообразным.4. Запрещены обратные зависимости: DAO не должен обращаться к Logic или Controller; Logic не должен обращаться к Controller.5. Требования к файловому DAO1. Используйте файл resources/catch_records.txt или другой явно документированный путь внутри структуры проекта.2. Каждый улов хранится одной строкой. Формат полей (включая поле waterBody) определите самостоятельно (например, разделение через символ ;) и опишите в файле README.3. После перезапуска приложения ранее сохранённые записи должны успешно загружаться и быть доступными через команды просмотра, поиска SHOW_ALL и расчёта статистики.4. CREATE_RECORD добавляет новую запись в конец файла, а CHANGE_STATUS обновляет изменённую запись, не создавая дубликата в файле.5. Автоматически назначаемые id не должны повторяться, даже если файл уже содержит данные.6. Пустой или ещё не существующий файл должен обрабатываться как отсутствие записей в базе, а не как критическая ошибка приложения.7. Файловые ресурсы необходимо закрывать корректно; рекомендуется try-with-resources.Не требуется. База данных, JSON/XML-библиотеки, Spring, графический интерфейс, многопоточность и сетевое взаимодействие не входят в это задание.6. Обработка ошибок1. Неизвестная команда должна обрабатываться отдельной командой и возвращать понятный ответ.2. Отсутствующий параметр, неверное число, неизвестный status и нарушенный формат запроса не должны приводить к необработанному exception в консоли.3. Ошибки файловой системы оборачиваются в DaoException.4. Logic переводит DaoException в LogicException, не раскрывая DAO верхнему слою.5. Controller/Command преобразует LogicException в пользовательское сообщение; stack trace не является пользовательским ответом.6. Не перехватывайте Exception без необходимости и не оставляйте пустые catch-блоки.7. Рекомендуемая последовательность работы1. Опишите класс модели CatchRecord (с полем waterBody), enum RecordStatus и бизнес-правила переходов.2. Наметьте пакеты и зависимости; до реализации убедитесь, что каждый слой знает только нижележащий контракт.3. Определите интерфейсы DAO и Logic, включая checked exceptions слоёв.4. Реализуйте и отдельно проверьте файловый DAO: сохранение, чтение, обновление и генерацию id.5. Реализуйте logic-слой и бизнес-проверки без строковых controller-запросов.6. Добавьте Command-реализации, CommandProvider и Controller.7. Соберите приложение в Main и выполните все контрольные сценарии.8. Проверьте структуру проекта, README и архив перед отправкой.Это не готовый алгоритм решения. Последовательность помогает не смешивать слои, но конкретные сигнатуры методов, формат хранения и способ связывания объектов студент проектирует самостоятельно.8. Обязательные контрольные сценарииДля проверки работоспособности в классе Main реализуйте выполнение следующей цепочки вызовов:1. Создать не менее двух корректных записей с разными рыбаками, водоёмами и видами рыб (команда CREATE_RECORD).2. Выполнить SHOW_ALL и убедиться, что обе записи корректно выводятся со всеми полями (включая водоём), начальным статусом NEW и присвоенными id.3. Для первой созданной записи последовательно изменить статус по цепочке: NEW → VERIFIED → REGISTERED → ARCHIVED.4. Попытаться выполнить запрещённый переход (например, из NEW сразу в ARCHIVED) и убедиться, что статус записи в файле не изменился.5. Выполнить поиск улова по части наименования рыбы без учёта регистра (команда FIND_BY_FISH).6. Выполнить поиск улова по части названия водоёма без учёта регистра (команда FIND_BY_WATERBODY).7. Выполнить команду GET_STATS для получения сводных данных по конкретному рыбаку и убедиться, что расчёт (количество уловов, сумма веса, максимальный улов) выполняется корректно.8. Выполнить SHOW_ACTIVE и убедиться, что записи со статусом ARCHIVED или CANCELLED не выводятся в результатах.9. Передать некорректную команду, а также как минимум два запроса с ошибками: например, с некорректным значением quantity=0, слишком коротким названием водоёма или отсутствующим параметром fisherman.10. Перезапустить приложение и подтвердить, что сохранённые данные считываются из файла, а новый id не дублирует существующий.9. Требования к сдаче1. Eclipse-проект с исходным кодом и файлом данных в папке ресурсов.2. Файл README.md с кратким описанием предметной области, рхитектуры, формата файла и инструкцией запуска.3. В README.md приведите список всех поддерживаемых команд и по одному примеру текстовых запросов для команд CREATE_RECORD, CHANGE_STATUS, FIND_BY_WATERBODY и GET_STATS.4. Архив не должен содержать bin, .class, служебную workspace-папку .metadata или временные файлы IDE.5. Проект должен компилироваться и запускаться под Java 25 без внешних зависимостей.
